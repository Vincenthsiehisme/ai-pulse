# 變異盤點：測試自己有沒有在守東西

> 這份文件是**規格**，`scripts/mutations.yaml`（清單）與 `scripts/mutate.py`（跑法）
> 是它的實作。三者不一致時以本檔為準，**先改本檔再改碼**（紅線 9）。

## 為什麼要有這一層

`health-alarms.md` 講的是「警報自己把自己關掉」。這一份講的是再上面一層：
**測試自己有沒有在守東西**。

2026-07-26 當天 selftest 是 224 條。224 是一個很好看的數字，而它回答不了唯一重要的
那個問題：**把碼改壞，會不會有東西紅？** 同日實測，把 `pulse-monitor.py` 的 `main()`
結尾 `return rc` 改成 `return 0`——整條鏈紅不紅就靠這個數字——selftest **224/224
全過**。224 條測試，一條都沒動。

（「幾條」這個數字本身不必再追。它會隨著補測試一直長，而它長多少跟守不守得住
沒有關係——那正是這一節在講的事。要看守不守得住，跑 `python3 scripts/mutate.py`。）

這是同一個病的第五個實例：**用「測試有幾條」代理「壞掉會不會被抓到」**。
兩者在正常路徑上正相關，所以平常看不出來；分岔的那天，正好就是碼被改壞的那天。

量「壞掉會不會被抓到」只有一個誠實的方法：**真的把碼改壞，看有沒有紅**。

## 為什麼不能用手做

2026-07-26 之前做過一輪手工的：一條一條 `sed` 進去、跑 selftest、看幾條紅、再還原。
結論是「94 個注入點裡 47 個存活」。那句話寫進 BACKLOG 的當天就開始腐爛——它是
**174 條測試**時量的，一週後 selftest 長到 224 條，那個比例已經沒有任何意義，
但它還印在清單上，看起來像個現況。

手工盤點的產物是**一個數字**；數字會過期，而過期不會讓任何東西變紅。
可重跑的產物是**一個判準**；判準會自己更新。

手工那輪還踩到兩個坑，兩個都必須寫進工具裡，否則工具會重蹈覆轍：

### 坑一：針腳不唯一，會假裝成「存活」

needle `'        if r.get("unenriched_undated"):'` 在 `pulse-monitor.py` 裡命中兩處
（console print 區塊與 `[alert]` 區塊都是 8 格縮排）。`str.replace(a, b, 1)` 改到了
前者，於是 alert 那條路徑根本沒被動過，selftest 全綠——差一點就得出「這個釘子
不存在」的結論，然後去補一條早就存在的測試。

規則：**注入前先 `assert 出現次數 == 1`**。次數不是 1 的條目一律判為
**stale（清單過期）**，不是「通過」。stale 要跟 survivor 一樣讓工具回非零——
一份自己悄悄跳過條目的清單，就是一顆永遠綠的燈。

### 坑二：改壞語法不算變異

一個讓 `render()` 直接 raise 的改動會讓 selftest 紅，但那紅的是崩潰、不是斷言。
把它算成「殺掉了」，等於用「碼能不能跑」代理「碼對不對」——又一個比事實寬鬆的
代理指標。

判準是 selftest 的最後一行：selftest 是一支平鋪的腳本，任何未捕捉的例外都會讓它
**印不出 `N/M passed`**。所以：

| selftest 輸出 | 判定 |
|---|---|
| 有 `N/M passed`，且 fails > 0 | **killed**（測試抓到了） |
| 有 `N/M passed`，且 fails = 0 | **survived**（沒有任何測試在守這裡） |
| 沒有那一行 | **crashed**（這個變異無效，不算數，要換一個） |

crashed 跟 stale 一樣要回非零：它代表清單裡有一個條目已經不是有效的變異了。

實例（2026-07-26）：M13 原本寫的是「在既有事件那一支再蓋一次 `ingested_at`」，
注入後縮排對不上，selftest 印不出結尾那行。**那是改壞語法，不是變異。**
若沒有這條判準，它會被記成「殺掉了」，而那一格其實從來沒被測過。改寫成一個
同樣痛、但語法合法的單行替換之後，它是真的被殺。

### 坑三：一條「每次注入都會紅」的檢查，會把 kill 訊號變成常數

下一節那條「每個 `find` 在目標檔案裡剛好出現一次」的檢查，第一次接上去就出事了：
mutate.py 跑到某一條時，那一條的針腳**正被它自己換掉**，於是這條檢查必紅。
結果是**每一條變異都「被殺」**——包含四條早就知道守不住的（M01/M02/M03/M11），
全部被誤判成 killed。

一個對所有輸入都給同一個答案的訊號，資訊量是零。這跟 `return 0` 的 CI、跟
`survives: true` 填滿的清單是同一件事，只是這次它長在量測工具自己身上。

規則：注入期間，mutate.py 用環境變數 `MUTATE_IN_FLIGHT=<id>` 告訴 selftest
「這一條的針腳現在本來就不該在」，selftest 只跳過**那一個 id**，其餘十九條照數。
基準線那一輪不設這個值。CI 也不設——只有 mutate.py 設它，而且一次一個。
selftest 另有一條釘住「`MUTATE_IN_FLIGHT` 只認得清單裡的 id」，免得打錯字就
等於憑空關掉一條檢查。

## 清單記的是「量到的事實」，不是「希望的樣子」

每個條目都帶一個 `survives:` 欄位，記的是**上次實測的結果**。工具在**兩個方向**
都比對：

- 記 `survives: false`，實際存活 → **回歸**。有測試被刪掉、或碼被改得繞過了測試。
- 記 `survives: true`，實際被殺 → **記錄過期**。有人補了測試但沒更新清單。

只釘一個方向的話，把 `survives: true` 全部填上去就會永遠綠——那是把清單變成一份
許願單。理由跟覆蓋率那一節、跟 exit code 那一節一樣：**一個天天紅的 CI 跟一個
永遠綠的 CI 一樣沒有資訊**，而一份永遠對的清單什麼都沒說。

`survives: true` 的條目**必須**寫 `why`，講清楚為什麼現在守不住、以及誰在管
（通常是 BACKLOG 的某一條）。已知的缺口掛在那裡是誠實（紅線 8）；沒有理由的
`survives: true` 是掩蓋。

## 不准弄髒工作區

工具會真的改原始碼檔案。三道護欄：

1. **開跑前**：目標檔案在 `git status --porcelain` 裡有任何改動就拒跑。
   已經髒的樹出事時分不清哪些改動是誰的。
2. **每一輪**：原文存在記憶體，還原走 `try/finally`，Ctrl-C 也還得回來。
3. **收工後**：逐檔比對 sha256 與開跑前一致，不一致就大聲叫並回非零。
   還原失敗而沒人知道，就是把變異過的碼 commit 上去。

工具**不做** git 操作、不 commit、不 push。它只讀寫那幾個目標檔案。

## 這一層不保證什麼

- **不保證測試是對的。** 一條斷言了恆真條件的測試也會讓變異變紅。
  變異測試量的是「有沒有東西在守」，不是「守的東西對不對」。
- **不保證覆蓋完整。** 清單是人挑的，挑漏了不會有人知道。它回答的是
  「我列出來的這些地方守不守得住」，不是「所有地方」。所以條目要挑
  **壞掉最痛的**那些，不是最好寫的那些。
- **不取代 selftest。** selftest 每次 push 都跑、0.5 秒；變異盤點跑 N 次 selftest，
  是分開的一條工作流。selftest 只快速檢查清單的針腳還在不在（見下）。

## selftest 這邊只做一件事：快速抓清單過期

`scripts/mutate.py` 要跑幾十次 selftest，太慢，不適合掛在每次 push 上。但
「清單過期」這件事不需要跑變異就查得到——只要數一下每個 `find` 在目標檔案裡出現
幾次。所以 selftest 釘的是：

- `mutations.yaml` 讀得進來，`id` 不重複，必填欄位都在。
- **每個 `find` 在它的目標檔案裡剛好出現一次**（注入期間略過 `MUTATE_IN_FLIGHT`
  指到的那一個，理由見坑三）。
- 每個 `survives: true` 的條目都有 `why`。

這樣改碼的人在 0.5 秒內就會知道清單需要跟著改，不必等到週一那班。

順帶把「修好了但沒併進 `main` 的，算沒修」這句話量化了一次：這四條在

## 第五輪（2026-07-26 傍晚，`fix/gate-keys-unmarked`）

**32 條：32 被殺、0 存活。** 新增 M29–M32，守 `gate.yaml` 的標記涵蓋檢查
（規格 `references/gate-config-status.md`）。

四條守的是同一條檢查的四種**安靜死法**：列舉回空 list（沒有 leaf 就沒有東西
違規，三條檢查同時變成永遠綠）、⚠ 不再是必要的（散文裡順口提一句「未接線」

檢查，跟一條「沒有東西可以違規」的檢查，輸出一模一樣。** 所以 selftest 裡另外
放了一個哨兵，直接釘住列舉到的 leaf 數量。

這一輪真正的收穫不是那四條被殺，而是 **M30 第一輪存活**。它守的那條測試我剛
寫完、也確實跑過、也是綠的——但它比對的是 `[e["path"] for e in parse(...)]`：
不管標記規則認不認得那三個字，列舉出來的 path 都是 `a.b`。**那條測試從頭到尾
沒有在測任何東西，而 322/322 全綠不會告訴你這件事。** 改成比對
`(path, unwired)` 之後才殺得掉。

也就是說這一輪至少有一條測試，是靠變異測試才發現它是空的。新寫的判準自帶
一批「判準自己的單元測試」時，這種空測試特別容易寫出來——因為手上有的是
剛寫好的函式，順手比對一個一定會成立的欄位，看起來跟真的一樣。

**記在這裡是因為它會再犯**：任何一條會讓程式多打一次網路的變異，在沒有外網的
環境裡都會變成 crash。變異要挑**只改判斷、不改 I/O 路徑**的那一行。

觀測到）、`no_baseline`（上一版是舊 schema，沒記名次）在畫面上有兩種說法、
資料層是三個值。看起來多一個，但少了它，「這版上線第一天整榜都沒有箭頭」
就查不出原因——共用一個值的話，那天看起來會像整批 repo 同時新出現。

而 `entered` 刻意**不給位移名次**：榜外可能是第 26 名，也可能是第 300 名，
`top_n` 以外沒有名次這回事。給一個算出來的數字就是 M181。

### 這一格的負數，最常見的成因不是時鐘

`stale_after_days` 那邊的負數是「有人寫了一個未來日期的語料目錄」。這一格不是。

判準讀 `git log`，而 `git log` 對「這顆 commit 有沒有推上去」一無所知。Actions
那一邊沒差（工作區從 `main` checkout，看到的都在遠端），**潤稿那一邊正好相反**：
它自己會建一顆 `nightly: enrich`，然後那顆 push 失敗、容器被回收。它若也開這支
旗標，就會讀到自己剛建的那顆，回報「今天剛推回來」。

實測 2026-08-07（模擬容器）：本地 commit 了 `nightly: enrich + narrative 2026-08-06`、
沒推，警報回「最後一次推回 2026-08-07（-1 天前）」，**不叫、綠燈**。
一支專門用來抓「那一邊默默失敗」的警報，由那一邊自己來量，永遠是綠的。

所以訊息刻意不寫「量不到」——那個詞在這支腳本裡保留給不觸警的淺 clone 與非 git
工作區。混用會讓讀的人以為這一格不叫，然後往錯的方向找一整晚。

對話裡。這個 repo 已經證明過很多次，只活在文件裡（更別說只活在對話裡）的規矩，
會在有人「順手補齊」的那天消失。

判準量的是**命令列**不是整份文字：只挑同時帶 `pulse-monitor` 與警報旗標的行。
散文要能解釋為什麼不准（runbook 步驟 17 底下那段就是），所以不能像 M202 第一版
那樣整份文字找字串——那正是這條分支上犯過四次的「判準抓到隔壁那一處」。

### 沒有做的那一半，寫下來

更根本的修法是讓判準去問「這顆 commit 在不在遠端分支上」，而不是問 `git log`。
沒走那條，是因為兩邊環境到底有沒有 `origin/main` 這個遠端追蹤 ref **還沒實測過**

先把成本低、量得到的那一半接上，另一半留在 `references/health-alarms.md` 裡。

## 第四十一輪（2026-08-11，`feat/a-watchdog-outside-the-chain`）

M222／M223／M224／M225。四條全部被殺（基準線 730/730）。

### 這一輪守的不是判準，是「距離」

`pulse-watchdog.py` 的判準本身很淺——四個日期、一個門檻、一個減法。
真正的設計全部在**它跟被監看的那條鏈之間的距離**上，而距離這種東西
在碼裡長得像「什麼都沒有」：另一支 workflow、另一個 concurrency group、
另一個時間、**沒有** `environment:`、**沒有** import pipeline 模組、
自己的 config key。

沒有東西守的話，這六個「沒有」會在未來某一次順手整理裡被填回去，
而且填回去的人會覺得自己在收斂重複。M222／M223／M225 就是那三種順手：

```
M222  group: watchdog → group: nightly     「兩個排程共用一組比較乾淨」
M223  補上 environment: github-pages        「其他 workflow 都有」
M225  讀 monitor 那個 key                   「兩個門檻都叫 stale_after_days，合併」
```

三條都不是錯字，三條都像重構。**而三條都會讓這一支在它唯一該叫的那一刻閉嘴**：
M222 讓它跟卡住的那一班一起排隊、M223 給它一個跟 2026-08-09 完全相同的單點、
M225 讓「為了讓 monitor 安靜而調鬆門檻」順便調鬆最後一道。

### M224：同一條規則的第三個消費者

`references/health-alarms.md` 三條規則的第 3 條是「負數的 lag 不算數」。
這條規則在這個 repo 已經漏接過兩次：`pulse-monitor.py` 的 enrich 那一格
（8/10 補的），以及在那之前的來源層。這一支是**第三個**消費者。

規則寫在文件裡、每個消費者各自實作一次——這個形狀本身就是問題，
而目前的補法只有「每新增一個消費者就補一條變異」。這不夠好，但至少
它會在下一個消費者忘記時變紅。真正的修法是把它收成 `lib` 裡的一個函式，
留給下一輪。

### 一個 cron 例外，用具名清單而不是放寬規則

selftest 原本有一條：**每天固定一班的 cron 必須跑在 16:00Z**。
watchdog 跑 `0 4 * * *`（台北中午），刻意跟被監看的那條鏈錯開時間——
同一個時刻跑的話，共用的那個外部故障（GitHub 排程整體延遲）會同時打中兩邊。

於是判準必須開一個例外。開法有兩種：

```
放寬規則   把「固定一班」的條件加上「除非 workflow 名字含 watch」→ 下一支叫什麼都自動豁免
具名清單   _CRON_1600_EXEMPT = {"watchdog.yml"}                  → 第三支每日班會直接紅
```

選了後者。理由跟第三十一輪〈順手拿掉一個空操作〉同一條：
**一個會自己擴張的例外，等於沒有規則**。具名清單的成本是「新增每日班時要動判準」，
而那個成本正是我們要的——它逼人在那一刻說明為什麼這一支不跑 16:00Z。

### M246 第一版存活：成功路徑上，丟掉 stderr 沒有任何差別

第一版加的是「子行程要回 0、stderr 要是空的」。而正常情況下 stderr 本來就是空的
——把 `return p.returncode, p.stdout, (p.stderr or "")` 改成回 `""`，
所有斷言照樣綠。

補法是**故意讓子行程失敗**：丟一個不存在的旗標進去，argparse 會回非零、

教訓比「規則存在 ≠ 規則被套用」再進一步：**只在成功路徑上測，測不到錯誤路徑上
的東西**。而錯誤路徑正是這一整條改動存在的理由——它只在壞掉的那一天有用，
所以它也只能在「讓它壞掉」的測試裡被守住。

## 第四十七輪（2026-08-11 夜，`fix/the-format-the-machine-writes`）

### 發生了什麼

`capabilities:` 那 97 行我手寫成 **4 空格**縮排。而 `sources.yaml` 這個檔其他序列
都是 2 空格，ruamel 吐出來的也是 2 空格。

平常沒事——因為 `--apply` 只在真的有異動要寫回時才動這個檔。8/11 夜班有一條來源
狀態變了，`pulse-source-health.py --apply` round-trip 整份寫回，**97 行縮排全部從

```

```

### 真正的教訓不是縮排

是**「人手寫的格式」與「機器會吐的格式」必須一致**。

這個檔有兩個作者：人（改設定、加來源）與機器（`--apply` 寫回狀態）。
兩個作者對同一份文件有不同的排版習慣時，第一個踩到的不是排版，是**所有拿字串
去比對這個檔的東西**——變異針腳、diff 的可讀性、任何 grep 型的判準。

而且它的延遲很長：我寫下 4 空格是 8/11 早上，炸掉是 8/11 深夜，中間隔著兩個
完全綠燈的 PR。**沒有人會把這兩件事聯想在一起**，除非有東西把它們綁起來。

### 補法：不動點

selftest 加一條——`sources.yaml` 必須是 ruamel round-trip 的**不動點**：

```python
y = YAML(); y.preserve_quotes = True; y.width = 4096
dump(load(src)) == src
```

那兩行設定要跟兩支 writer 一致，否則測的就不是真的會被寫回去的格式。

成本是 CI 上多一次 round-trip（毫秒級），換到的是**在手寫 YAML 的那一刻就知道**，
而不是等機器某天心血來潮 `--apply` 才知道。

M250 就是把縮排改回 4 空格，驗證這條真的會紅。

### 順帶記一件事：紅燈是對的，順序是可以討論的

夜班的步驟是

```
17. Commit & push data changes
18. Config invariants (selftest)
```

**判準排在 commit 之後**——所以那份被機器重排過的 `sources.yaml` 已經推上 main 了，
selftest 才紅。它是事後報告，不是閘門。

這次沒有造成損害（機器重排的結果本身是對的，錯的是我的針腳），
但值得記下來：**這條鏈目前沒有任何一步擋得住壞資料進 main。**
要不要改成閘門是另一個題目——資料 commit 被 config 判準擋住也有它的代價。

## 第四十八輪（2026-08-12，`fix/shard-the-mutation-run`）

沒有新變異。這一輪修的是**跑變異這件事本身撞牆了**。

### 量出來的牆

```
selftest 單次   4.6 秒
清單            248 條
248 × 4.6      ≈ 19.0 分鐘
workflow 上限   20 分鐘
```

8/12 的 PR #178 整班被砍。CI 的第二條錯誤訊息是
「mutate.py 跑完後工作區不乾淨——原始碼沒還原回去」——那**不是另一個 bug，
是被砍的後果**：mutate.py 改了原始碼、還沒還原就被 SIGKILL。

這件事我在容器裡重現過一次（把工具的逾時設成 2 分鐘），留下的正是同一個
`M scripts/pulse-render.py`。**還原護欄運作正常，它只是沒有機會跑。**

### 為什麼不是「只跑改到的檔案那幾條」

這是最直覺的省時法，而它**不成立**。

一條變異被殺，靠的是 selftest 裡某一條判準。**改 selftest 可以在完全不碰被變異的
那個檔的情況下，讓某一格從此不再被守住。** 依改動檔案篩選，正好漏掉這個 repo
最在意的那一種失效——而這一整支腳本存在的理由，就是抓那一種。

（這一輪之前的三輪裡，M240／M242／M243／M246 四條第一版存活，全部是
「判準沒接上」而不是「碼改壞了」。依檔案篩選對這四條一條都攔不到。）

### 為什麼不是「把 timeout 調大」

清單只會變長。今天 248，這個月加了 25 條。調大只是把同一道牆往後挪，
而且下一次撞牆的人不會知道它撞過一次。

### 分片：切法是取模，不是分組

```
shard(items, k, n) = [it for i, it in enumerate(items) if i % n == k - 1]
```

**依索引取模，不依檔案分組。** 分組的話 `pulse-render.py` 那 57 條會擠在同一片，
那一片的耗時跟不切幾乎一樣——切了等於沒切。

取模之後 4 片各 62 條、每片約 4.7 分鐘，實測跑完 shard 4/4 是
`62 條：62 被殺、0 存活、0 要人管`，工作區乾淨。

### 分片必須是一個分割，而且要有東西釘住

**一條變異因為切片邏輯而從來沒被跑過，是這支腳本最糟的失敗方式**：
清單看起來很完整，而其中一格從來沒有人驗過。而且它**不會紅**——
沒跑到的那一條當然不會回報失敗。

所以 selftest 加三條：

```
n 片的聯集等於全部，且兩兩不相交
workflow 的 matrix 片數與 --shard 的分母一致（兩個數字寫在不同地方）
壞掉的 --shard 規格一律拒跑，不猜
```

第二條特別容易腐爛：`matrix: [1,2,3,4]` 與 `--shard ${{ matrix.shard }}/4`
是兩個各自獨立的數字，有人加第五片而忘了改分母的話，會**靜靜地少跑一整片**。

## 第五十一輪（2026-08-12，`fix/the-ledger-that-erased-itself`）

### 冪等要冪等到帳目那一層才算數

那支遷移的資料層是冪等的：第二次跑什麼都不改，`要寫的檔：0`。
但帳目寫在 `--apply` 的**無條件路徑**上：

```python
if not args.apply:
    return 0
for path, text in sorted(writes.items()):   # writes 是空的，這圈不跑
    atomic_write_text(path, text)
atomic_write_text(.../f"{TAG}.json", ...)   # ← 這行照跑
```

於是第二次 `--apply`——**那一次它完全正確地什麼都沒做**——把上一次的紀錄
整份覆蓋成全 0，而全 0 的那份進了 commit：

```
_probe/identity-repair-2026-08-12.json
  corpus: 0, titles: 0, moved: 0, created: 0, rescored: 0
```

一個寫著「這次遷移什麼都沒做」的檔案，躺在一個改了 53 個檔的 commit 旁邊。

### 為什麼這比「沒有帳目」更糟

沒有帳目的時候，人會去翻 diff。
**有一份說謊的帳目時，人會相信它。**

而它說的謊特別難反駁：全 0 是一個合法的值——遷移本來就可能什麼都沒做。
光看那個檔分不出「這次沒事做」與「上次做了但被洗掉」。

### 這一輪抓到它的不是測試，是人去看真實資料

selftest 有一條測「跑第二次要什麼都不寫」，它測的是 `要寫的檔：0`——
**帳目不在那個計數裡**。所以那條測試在冪等這件事上是綠的，
而冪等的一半是壞的。

補的測試改成直接比對檔案內容：第二次跑完，帳目要一字不差。

2026-08-11 已經演過一次同型事故（人手寫 4 空格、機器吐 2 空格，

新增的第三條檢查是「`scripts/` 裡 import 的第三方套件都要在 `requirements.txt`
或例外表裡」。跑起來的第一件事就是它報出：

```

```

那段是 `try: import opencc / except ImportError: simp_trad = False`，
而 14 份夜班報告每一份都印著「簡繁正規化：**未啟用**」。

**行為是對的**（量不到就說量不到），但「從來沒裝過」在此之前
**只寫在報告的一行字裡**，沒有任何地方把它記成一個決定。
現在它在例外表裡，旁邊有理由，而且有一條測試釘住「例外表裡的每一項
都真的還被 import」——一個沒有人 import 的例外會留在表裡當成「我們考慮過」。

### 一個踩到的坑：selftest 是一個幾千行的單一命名空間

第一版的迴圈變數用了 `_wf`，而那個名字在 2319 行已經是另一段的 workflow

**沒有任何 lint 會抓這個**（兩處都是合法的全域指派）。抓到它的是「跑一次」。
這支腳本沒有函式作用域可以保護變數，新增區塊的迴圈變數要自己加前綴。

### 一條在 CI 上永遠證明不了的保護

第 3 條檢查第一版直接用 `sys.stdlib_module_names`——**那一格是 Python 3.10
才有的**。CI 跑 3.12、開發容器跑 3.11，所以兩邊都全綠。而人在 macOS 上跑

**selftest 跑不起來的機器，等於那台機器上一條檢查都沒有。**
這比少一條檢查嚴重：少一條是知道自己少了什麼，跑不起來是什麼都不知道。

修法是加 fallback（`find_spec` 看模組解析出來的檔案在不在標準庫目錄底下），

```
M271  打 fallback 本身（拿掉 frozen 分支）      → 殺得掉
M272  拿掉 getattr 保護                        → 記成已知存活
```

M272 只有在 3.10 以下的直譯器上才殺得掉。**它不是漏網，是這個工具的邊界**：
CI 只有一個 Python 版本，而這條保護守的是 CI 沒有的那些版本。
所以照實記進 `survives: true` 並寫下出處，而不是刪掉它假裝沒這回事。

## 第五十六輪（2026-08-13，`feat/read-only-what-they-offer`）

M278–M284，七條第一版全殺。守的是摘要補抓那一層的**合規邊界**。

### 這一輪守的不是「會不會壞」，是「可不可以做」

前面五十五輪釘的多半是正確性：算錯、漏掉、判反。這一輪不同——
碼寫得再對，只要它去讀了不該讀的那一頁，這套系統的立足點就沒了。

所以七條裡有五條的內容是「拿掉一道限制」而不是「弄壞一個計算」：

```
M278  不看主機          feed 指到別的網域也照抓
M279  不看白名單        excerpt_fetch 變成全點開
M280  不看上限          一班對別人站台連發
M281  連 feed 給的也重抓  請求量翻倍，而且沒有必要
M282  抓不到拿標題充數    紅線 2：把「讀不到」寫成「摘要就是標題」
```

這一類的特徵是**放寬之後什麼都不會壞**：語料變多、摘要變滿、潤稿寫得出來，
每一個指標都往好的方向動。沒有變異盤點的話，這五條裡沒有一條會有人發現。

### M284 是這個 repo 第一條打在設定檔上的變異

它把 `excerpt_fetch: true` 加到 `src-xai-news` 上——而 x.ai 的 robots.txt
公開宣告 `Content-Signal: ai-train=no, search=yes, **ai-input=no**`。

前面 283 條全都打在 `scripts/` 或 `requirements.txt` 上，因為那些是「碼會不會做錯事」。
這一條打在 `_config/` 上，因為這裡要守的是「**人會不會把不該開的開起來**」，
而那個動作只需要在 YAML 裡多打一行 `true`，不需要動任何一行碼。

判準寫在 selftest 的三條設定檔斷言裡（ai-input=no 不得開、license_note 沒寫
excerpt 不得開、今天開著的就是那一條）。M284 是它們的執法證明。

### M283 又是消費端

`fill_missing_excerpts()` 的判準全部釘好之後，把 `run_source` 裡那一行呼叫拿掉
——**判準一條都不會紅**。這是三天內第二次（上一次是 M274 的 `missing = unbucketed(seen)`）。

`run_source` 要跑起來得先有實體表、state 與 seen，端到端成本太高，

文字釘比行為釘弱，這點要說清楚：它擋得住「被刪掉」，擋不住「還在但沒作用」。
記在這裡，是為了讓下一個人知道這一格的保護只到哪裡。
