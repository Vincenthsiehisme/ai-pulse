# 變異盤點：測試自己有沒有在守東西

> 這份文件是**規格**，`scripts/mutations.yaml`（清單）與 `scripts/mutate.py`（跑法）
> 是它的實作。三者不一致時以本檔為準，**先改本檔再改碼**（紅線 9）。

## 為什麼要有這一層

`health-alarms.md` 講的是「警報自己把自己關掉」。這一份講的是再上面一層：
**測試自己有沒有在守東西**。

2026-07-26 當天 selftest 是 224 條。224 是一個很好看的數字，而它回答不了唯一重要的
那個問題：**把碼改壞，會不會有東西紅？** 同日實測，把 `pulse-monitor.py` 的 `main()`
結尾 `return rc` 改成 `return 0`——整條鏈紅不紅就靠這個數字——selftest **224/224
全過**。224 條測試，一條都沒動。

（「幾條」這個數字本身不必再追。它會隨著補測試一直長，而它長多少跟守不守得住
沒有關係——那正是這一節在講的事。要看守不守得住，跑 `python3 scripts/mutate.py`。）

這是同一個病的第五個實例：**用「測試有幾條」代理「壞掉會不會被抓到」**。
兩者在正常路徑上正相關，所以平常看不出來；分岔的那天，正好就是碼被改壞的那天。

量「壞掉會不會被抓到」只有一個誠實的方法：**真的把碼改壞，看有沒有紅**。

## 為什麼不能用手做

2026-07-26 之前做過一輪手工的：一條一條 `sed` 進去、跑 selftest、看幾條紅、再還原。
結論是「94 個注入點裡 47 個存活」。那句話寫進 BACKLOG 的當天就開始腐爛——它是
**174 條測試**時量的，一週後 selftest 長到 224 條，那個比例已經沒有任何意義，
但它還印在清單上，看起來像個現況。

手工盤點的產物是**一個數字**；數字會過期，而過期不會讓任何東西變紅。
可重跑的產物是**一個判準**；判準會自己更新。

手工那輪還踩到兩個坑，兩個都必須寫進工具裡，否則工具會重蹈覆轍：

### 坑一：針腳不唯一，會假裝成「存活」

needle `'        if r.get("unenriched_undated"):'` 在 `pulse-monitor.py` 裡命中兩處
（console print 區塊與 `[alert]` 區塊都是 8 格縮排）。`str.replace(a, b, 1)` 改到了
前者，於是 alert 那條路徑根本沒被動過，selftest 全綠——差一點就得出「這個釘子
不存在」的結論，然後去補一條早就存在的測試。

規則：**注入前先 `assert 出現次數 == 1`**。次數不是 1 的條目一律判為
**stale（清單過期）**，不是「通過」。stale 要跟 survivor 一樣讓工具回非零——
一份自己悄悄跳過條目的清單，就是一顆永遠綠的燈。

### 坑二：改壞語法不算變異

一個讓 `render()` 直接 raise 的改動會讓 selftest 紅，但那紅的是崩潰、不是斷言。
把它算成「殺掉了」，等於用「碼能不能跑」代理「碼對不對」——又一個比事實寬鬆的
代理指標。

判準是 selftest 的最後一行：selftest 是一支平鋪的腳本，任何未捕捉的例外都會讓它
**印不出 `N/M passed`**。所以：

| selftest 輸出 | 判定 |
|---|---|
| 有 `N/M passed`，且 fails > 0 | **killed**（測試抓到了） |
| 有 `N/M passed`，且 fails = 0 | **survived**（沒有任何測試在守這裡） |
| 沒有那一行 | **crashed**（這個變異無效，不算數，要換一個） |

crashed 跟 stale 一樣要回非零：它代表清單裡有一個條目已經不是有效的變異了。

實例（2026-07-26）：M13 原本寫的是「在既有事件那一支再蓋一次 `ingested_at`」，
注入後縮排對不上，selftest 印不出結尾那行。**那是改壞語法，不是變異。**
若沒有這條判準，它會被記成「殺掉了」，而那一格其實從來沒被測過。改寫成一個
同樣痛、但語法合法的單行替換之後，它是真的被殺。

### 坑三：一條「每次注入都會紅」的檢查，會把 kill 訊號變成常數

下一節那條「每個 `find` 在目標檔案裡剛好出現一次」的檢查，第一次接上去就出事了：
mutate.py 跑到某一條時，那一條的針腳**正被它自己換掉**，於是這條檢查必紅。
結果是**每一條變異都「被殺」**——包含四條早就知道守不住的（M01/M02/M03/M11），
全部被誤判成 killed。

一個對所有輸入都給同一個答案的訊號，資訊量是零。這跟 `return 0` 的 CI、跟
`survives: true` 填滿的清單是同一件事，只是這次它長在量測工具自己身上。

規則：注入期間，mutate.py 用環境變數 `MUTATE_IN_FLIGHT=<id>` 告訴 selftest
「這一條的針腳現在本來就不該在」，selftest 只跳過**那一個 id**，其餘十九條照數。
基準線那一輪不設這個值。CI 也不設——只有 mutate.py 設它，而且一次一個。
selftest 另有一條釘住「`MUTATE_IN_FLIGHT` 只認得清單裡的 id」，免得打錯字就
等於憑空關掉一條檢查。

## 清單記的是「量到的事實」，不是「希望的樣子」

每個條目都帶一個 `survives:` 欄位，記的是**上次實測的結果**。工具在**兩個方向**
都比對：

- 記 `survives: false`，實際存活 → **回歸**。有測試被刪掉、或碼被改得繞過了測試。
- 記 `survives: true`，實際被殺 → **記錄過期**。有人補了測試但沒更新清單。

只釘一個方向的話，把 `survives: true` 全部填上去就會永遠綠——那是把清單變成一份
許願單。理由跟覆蓋率那一節、跟 exit code 那一節一樣：**一個天天紅的 CI 跟一個
永遠綠的 CI 一樣沒有資訊**，而一份永遠對的清單什麼都沒說。

`survives: true` 的條目**必須**寫 `why`，講清楚為什麼現在守不住、以及誰在管
（通常是 BACKLOG 的某一條）。已知的缺口掛在那裡是誠實（紅線 8）；沒有理由的
`survives: true` 是掩蓋。

## 不准弄髒工作區

工具會真的改原始碼檔案。三道護欄：

1. **開跑前**：目標檔案在 `git status --porcelain` 裡有任何改動就拒跑。
   已經髒的樹出事時分不清哪些改動是誰的。
2. **每一輪**：原文存在記憶體，還原走 `try/finally`，Ctrl-C 也還得回來。
3. **收工後**：逐檔比對 sha256 與開跑前一致，不一致就大聲叫並回非零。
   還原失敗而沒人知道，就是把變異過的碼 commit 上去。

工具**不做** git 操作、不 commit、不 push。它只讀寫那幾個目標檔案。

## 這一層不保證什麼

- **不保證測試是對的。** 一條斷言了恆真條件的測試也會讓變異變紅。
  變異測試量的是「有沒有東西在守」，不是「守的東西對不對」。
- **不保證覆蓋完整。** 清單是人挑的，挑漏了不會有人知道。它回答的是
  「我列出來的這些地方守不守得住」，不是「所有地方」。所以條目要挑
  **壞掉最痛的**那些，不是最好寫的那些。
- **不取代 selftest。** selftest 每次 push 都跑、0.5 秒；變異盤點跑 N 次 selftest，
  是分開的一條工作流。selftest 只快速檢查清單的針腳還在不在（見下）。

## selftest 這邊只做一件事：快速抓清單過期

`scripts/mutate.py` 要跑幾十次 selftest，太慢，不適合掛在每次 push 上。但
「清單過期」這件事不需要跑變異就查得到——只要數一下每個 `find` 在目標檔案裡出現
幾次。所以 selftest 釘的是：

- `mutations.yaml` 讀得進來，`id` 不重複，必填欄位都在。
- **每個 `find` 在它的目標檔案裡剛好出現一次**（注入期間略過 `MUTATE_IN_FLIGHT`
  指到的那一個，理由見坑三）。
- 每個 `survives: true` 的條目都有 `why`。

這樣改碼的人在 0.5 秒內就會知道清單需要跟著改，不必等到週一那班。

順帶把「修好了但沒併進 `main` 的，算沒修」這句話量化了一次：這四條在

## 第五輪（2026-07-26 傍晚，`fix/gate-keys-unmarked`）

**32 條：32 被殺、0 存活。** 新增 M29–M32，守 `gate.yaml` 的標記涵蓋檢查
（規格 `references/gate-config-status.md`）。

四條守的是同一條檢查的四種**安靜死法**：列舉回空 list（沒有 leaf 就沒有東西
違規，三條檢查同時變成永遠綠）、⚠ 不再是必要的（散文裡順口提一句「未接線」

檢查，跟一條「沒有東西可以違規」的檢查，輸出一模一樣。** 所以 selftest 裡另外
放了一個哨兵，直接釘住列舉到的 leaf 數量。

這一輪真正的收穫不是那四條被殺，而是 **M30 第一輪存活**。它守的那條測試我剛
寫完、也確實跑過、也是綠的——但它比對的是 `[e["path"] for e in parse(...)]`：
不管標記規則認不認得那三個字，列舉出來的 path 都是 `a.b`。**那條測試從頭到尾
沒有在測任何東西，而 322/322 全綠不會告訴你這件事。** 改成比對
`(path, unwired)` 之後才殺得掉。

也就是說這一輪至少有一條測試，是靠變異測試才發現它是空的。新寫的判準自帶
一批「判準自己的單元測試」時，這種空測試特別容易寫出來——因為手上有的是
剛寫好的函式，順手比對一個一定會成立的欄位，看起來跟真的一樣。

**記在這裡是因為它會再犯**：任何一條會讓程式多打一次網路的變異，在沒有外網的
環境裡都會變成 crash。變異要挑**只改判斷、不改 I/O 路徑**的那一行。

觀測到）、`no_baseline`（上一版是舊 schema，沒記名次）在畫面上有兩種說法、
資料層是三個值。看起來多一個，但少了它，「這版上線第一天整榜都沒有箭頭」
就查不出原因——共用一個值的話，那天看起來會像整批 repo 同時新出現。

而 `entered` 刻意**不給位移名次**：榜外可能是第 26 名，也可能是第 300 名，
`top_n` 以外沒有名次這回事。給一個算出來的數字就是 M181。

### 這一格的負數，最常見的成因不是時鐘

`stale_after_days` 那邊的負數是「有人寫了一個未來日期的語料目錄」。這一格不是。

判準讀 `git log`，而 `git log` 對「這顆 commit 有沒有推上去」一無所知。Actions
那一邊沒差（工作區從 `main` checkout，看到的都在遠端），**潤稿那一邊正好相反**：
它自己會建一顆 `nightly: enrich`，然後那顆 push 失敗、容器被回收。它若也開這支
旗標，就會讀到自己剛建的那顆，回報「今天剛推回來」。

實測 2026-08-07（模擬容器）：本地 commit 了 `nightly: enrich + narrative 2026-08-06`、
沒推，警報回「最後一次推回 2026-08-07（-1 天前）」，**不叫、綠燈**。
一支專門用來抓「那一邊默默失敗」的警報，由那一邊自己來量，永遠是綠的。

所以訊息刻意不寫「量不到」——那個詞在這支腳本裡保留給不觸警的淺 clone 與非 git
工作區。混用會讓讀的人以為這一格不叫，然後往錯的方向找一整晚。

對話裡。這個 repo 已經證明過很多次，只活在文件裡（更別說只活在對話裡）的規矩，
會在有人「順手補齊」的那天消失。

判準量的是**命令列**不是整份文字：只挑同時帶 `pulse-monitor` 與警報旗標的行。
散文要能解釋為什麼不准（runbook 步驟 17 底下那段就是），所以不能像 M202 第一版
那樣整份文字找字串——那正是這條分支上犯過四次的「判準抓到隔壁那一處」。

### 沒有做的那一半，寫下來

更根本的修法是讓判準去問「這顆 commit 在不在遠端分支上」，而不是問 `git log`。
沒走那條，是因為兩邊環境到底有沒有 `origin/main` 這個遠端追蹤 ref **還沒實測過**

先把成本低、量得到的那一半接上，另一半留在 `references/health-alarms.md` 裡。

中欄從 1070 掉到 821，而索引 9 筆本來就是 814——**兩側的空白自己消失了**。

索引從 9 微調到 10 只是留緩衝，不是修法。把這件事寫進碼裡的註解，
是因為下一個人看到 `IDX_ITEMS` 會以為那是解法。

### M220 第一版存活：判準掃字串，掃到的是規則不是套用

第一版寫的是「`.lead-story.t-long h1` 在 CSS 裡」加「`t-long` 出現在原始碼裡」。
而 M220 拿掉的是 `lead_cls` 那一行**賦值**——CSS 規則還在、字串還在，
判準全綠。

改成走真的 `build_home()`，餵三種長度的標題，斷言輸出的 class 分別是
`lead-story t-long` / `lead-story t-mid` / `lead-story`。

這是這條分支上第五次同一個形狀：**在一整份原始碼裡找一個字串，然後以為
自己在守某一處**（M182 crash、M184 存活、M188 打中隔壁、M202 打中註解、
這次）。前四次的教訓是「把範圍縮小再問」，這次的是**「規則存在」不等於
「規則被套用」**——要問輸出，不要問原始碼。

### 右欄那兩組疊字，其中一組是常態不是例外

`journey_shape()` 在只有一筆證據時，把區塊標題換成 `EVIDENCE_HEADING`
——也就是那個區塊本身就是一份帶外連的證據清單。而底下又印一次 `ev_block`。

**94% 的已發布事件只有一筆證據**，所以那不是邊角案例，是絕大多數頁面的樣子。
一個只在少數情況下正確的版面，跟一個壞掉的版面差別不大。

## 第四十二輪（2026-08-11，`feat/what-each-source-can-ever-tell-us`）

M226–M230。五條全部被殺（基準線 734/734）。

### 這一輪守的是「驗收條件不准過期」

PRD 原本的 AC03 是一句話：「所有 running sources 都有 capability 定義。」
那句話在通過的那天成立，在下一次有人加來源的那天失效，而且**不會有任何東西變紅**。

所以判準寫在 selftest 不寫在文件，而 M226 打的就是那條判準的效果：
把一條 running 來源的 capabilities 清空，紅了才算數。

同一個形狀在這個 repo 已經記過一次（第三十一輪〈順手拿掉一個空操作〉）。
差別是那次守的是「一個看起來沒作用的呼叫其實有作用」，
這次守的是「一個看起來已經成立的條件其實隨時會不成立」。

### M226／M227 第一版是無效變異：打到判準本身

第一版把 `find` 指向 `selftest.py` 裡那兩行斷言，結果兩條都是 `regression`——
`734/734 passed`、沒有任何測試在守。

當然沒有。**把守衛拿掉，沒有第二個守衛會為此變紅**，這是恆真的，
量不出任何資訊。變異要打的是被守的東西（`_config/sources.yaml` 的資料），
不是守它的那隻手。

寫下來是因為這個錯誤很好犯：判準寫在哪裡，`find` 就很自然地指向哪裡。
判準是**量尺**，變異要打的是**被量的東西**。

### M228：把沒有人用的那一格從表上拿掉

`procurement`（有人真的付錢買了）目前 **0 條來源宣稱**。
一個很合理的順手整理是「沒人用，刪掉」——而那正是最該擋的一種改動：

> **盲區從清單上消失，不等於盲區被補上。**

那一格是 0，正是它必須留在表上的理由。刪掉之後，「這個系統看不到誰真的付錢買了」
這個事實就再也沒有地方顯示。

### M230：搬完家之後，要有東西擋住搬回去

`{"active", "degraded", "probing"}` 這輪從四個檔案收進 `lib/sources.py`
（`pulse-probe` / `pulse-monitor` / `pulse-source-notes`，以及在
`pulse-source-health` 裡叫 `RUNNABLE` 的那一份）。

搬家本身不會有人反對，會發生的是**下一次有人為了少一個 import 而寫回去**。
禁令比照既有的 `aggregator_sources` 字面值禁令，M230 驗證它真的會紅。

### 這一輪最後改的是一段我自己寫錯的話

第一版的 `references/source-capabilities.md` 寫「這一格不觸警，是因為上游那個
警報已經壞了」。查 `references/source-lifecycle.md` 之後發現寫錯了：那張表白紙黑字
寫著「`200` 但 0 筆 → 成功 `+8`」，理由是「安靜的 feed 是健康的 feed，
把『沒新聞』罰成失敗等於逼系統偏好吵的來源」。**那個判斷是對的。**

真正的缺口比「壞掉」更難看見：**那張表只看單班，而沒有任何消費者在看累計。**
一班 200／0 筆是安靜；25 班全部 0 筆、一次都沒有過，是這條線從來沒到過貨——
而兩者在健康分上都是 100。

順手把 `source-lifecycle.md` 裡那一列的例子也更正了：它原本寫
「`src-mistral-news` 連兩天 200／0 筆」，實際是 25 班 24 次成功、累計 0 筆。
**規格裡舉的例子也會過期，而過期的例子比沒有例子更容易誤導**。

## 第四十三輪（2026-08-11，`feat/what-we-cannot-answer`）

M231–M236。六條全部被殺（基準線 748/748），**其中 M236 第一版 crash**。

### 這一輪守的是「量不到不准印成 0」

覆蓋缺口矩陣的需求那一欄是人給的，而今天是 0 筆。
把「還沒有人回答過」印成 `0`，會讓 `procurement`（0 需求、0 來源）
看起來跟一個真的沒問題的格子一樣綠——而它其實是這個系統最大的盲區之一。

三條變異打的是同一件事的三個面：

```
M234  樣本不足時照樣給燈號    燈號是拿需求算出來的，需求量不到而燈照亮，亮的是空氣
M235  0 需求給綠燈            0 需求是「這一輪沒人問到」，不是「這一類沒問題」
M231  unanswerable 不填 reason 沒有原因碼的「看不到」只剩一個計數，補不出任何一列
```

`coverage-gap.json` 的 `other_ratio` 在量不到時是 `null` 不是 `0.0`，
理由同一條：兩者在 JSON 裡差一個字，在判斷上差一個「我們知道」與「我們不知道」。

### M233：兩份詞彙表就是兩個對不齊的軸

PRD §7 給了 11 個 reason、§14 給了 14 個 capability，而 §19 的矩陣要求兩者
可以直接比較。M233 把 `REASONS` 從 `CAPABILITIES | {"other"}` 改回 PRD 那份
硬寫的 11 個值——包含只在那一側存在的 `product_availability`。

用兩份清單 join 的後果不是報錯，是**有些列永遠對不到**：
`product_availability` 這一列永遠 0 條來源、`developer_feedback` 這一列永遠 0 需求。
兩者看起來都像量出來的洞，實際上是詞彙表的洞。

更根本的一句寫在規格裡：**「這個訊號我回答不了」的理由，本來就是一個能力請求。**
需求面與供給面講的是同一件事。

### M236 第一版 crash：判準用 `.index()`

順序判準原本寫 `_WF_SR.index("pulse-coverage-gap.py --write")`。
M236 把那一行 `run:` 換掉之後字串不見了，`.index()` 丟 ValueError，
selftest 整支炸掉、沒印出 `N/M passed`——`mutate.py` 記成 `crashed`，**不算數**。

改成 `find()`（不存在回 -1，順序判斷自然為假）之後紅得乾淨，2 條紅。

同一個形狀第三十輪的 M182 記過一次。當時的教訓是「判準自己不准炸」，
這次補一句更具體的：**在「東西不見了」這種變異上，判準必須把不見當成一個值，
不是當成一個例外。** 例外會讓判準跟被測的東西一起死，而死掉的判準不會紅。

### 一個順手改掉的分母

`pulse-signal-review` 的「已裁決 N 則」原本是 `len(history.read(led))`。
改成一次裁決寫兩筆之後，那個數字會把每一筆 `unanswerable` 算成兩則——
也就是**分母會隨著「答不了的比例」自己浮動**。

那比錯得離譜更難發現：它一直是個合理的數字，只是慢慢地偏。
改成 `read(led, field="verdict")`。`lib/history.read()` 本來就吃 `field=` 過濾，
兩筆制之所以選這個形狀，一半的理由就是它。
