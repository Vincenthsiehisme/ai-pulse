# 「沒有內容」有三種，不能寫成同一句話

> 消費者：`scripts/lib/availability.py`、`scripts/pulse-digest-prep.py`、
> `scripts/enrich-runbook.md` 的潤稿寫法。
> 規格先於實作（紅線 9）：這一頁先寫，碼才動。

## 觸發這一頁的那一則

2026-08-13 的夜間鏈潤了 `evt-2026-08-11-797106`（Introducing Grok Bot），寫出來是：

```
## 事實
xAI 在官網公告推出名為 Grok Bot 的新產品，並開出 x.ai/bot 專屬頁面…

## 脈絡     （證據不足，待補）
## 影響     （證據不足，待補）
## 判斷     （證據不足，待補）

## 下一個訊號
xAI 是否釋出 Grok Bot 的功能說明、使用文件或與 Grok 4.6 的關聯說明
```

**那份說明已經釋出了，就在 `https://x.ai/bot`——而那個連結躺在這一則自己的證據列裡。**

系統在等一個它手上已經有的東西。而它會一直等下去，因為沒有人會去看那個網址。

### 為什麼會這樣

語料裡那兩筆的 `summary` 都是空字串。空的原因不是頁面沒內容，是：

```
src-xai-news  license_note: titles + links only；
              站方另掛 Content-Signal: ai-train=no, search=yes, ai-input=no
```

**我們選擇不取。** 那是一個政策決定，而潤稿層把它寫成了證據狀態。

## 三種狀態

| 狀態 | 判準（可算） | 意思 | 要人做什麼 |
|---|---|---|---|
| `has_text` | 這一筆有摘要 | 內容在手上 | — |
| `unfetched` | 沒摘要，但來源允許摘錄 | **我們沒抓到**，是我們的缺口 | 去修抓取端 |
| `withheld` | 沒摘要，來源不允許摘錄 | **我們不取**，是政策 | 不用做任何事，把話寫對就好 |

`withheld` 底下還要分清楚是誰畫的線，因為對外的說法不同：

```
站方畫的   license_note 含 ai-input=no   → 站方宣告不希望內容被當成 AI 輸入
我們畫的   license_note 只寫「標題＋連結」 → 我們自己的保守約束
```

第一種不能改。第二種是我們的決定，要改要走 PR 並寫下理由
（見 `references/excerpt-fetch.md`）。

## 三種寫法

**`unfetched`**——不要寫進文章。這是我們的故障，該進診斷、該有人去修，
不該變成給讀者的一句「證據不足」。文章裡就當那一則只有標題。

**`withheld`**——寫出來，而且要給連結：

> xAI 宣告不希望內容被當成 AI 的輸入，所以我們只留標題與連結。
> Grok Bot 到底做什麼，直接看原文：https://x.ai/bot

**`has_text` 但真的很薄**——這才是原本那句「（證據不足，待補）」的正確用法：
來源給了，而它給的就是這麼多。

## 完整度的定義跟著改

一篇寫「（證據不足，待補）」的文章，是在告訴讀者**沒有更多可知道的**。
在 Grok Bot 那則上，那句話是假的，而且把讀者擋在門外。

一篇寫「站方不希望轉述，原文在這裡」的文章**更完整**——讀者知道缺什麼、
為什麼缺、去哪裡補。

**完整度不是「引用了多少」，是「讀者知不知道自己缺什麼」。**

## 對寫作框架的影響：多一個 D 層

`references/digest-framework.md` 的三層要變四層：

| 層 | 是什麼 | 跟 B 的差別 |
|---|---|---|
| A | 證據內 | |
| B | 背景知識（可查證，不在 vault） | **沒有連結，讀者補不了** |
| C | 作者推論 | |
| **D** | **一手來源有、我們沒取用** | **有連結，讀者自己補得了** |

D 可以機檢，判準在下一支（`pulse-digest-apply.py`）實作：
**引用到 `withheld` 來源的事件，文章裡必須有一條 D 級 claim 指向它的原文連結**，
沒有就退件。把「誠實」變成欄位，不靠寫的人記得。

## 門禁那一邊：`thin_fact` 也混了三種（2026-08-13 拆開）

上一版這裡寫「還沒做，記在 BACKLOG」，並且引用了「看板上 12 則 thin_fact」。
**那個 12 是錯的，我沒有去數就寫了。** 實際重算是 6 則（12 是 `stale_backfill`
的數字）。訂正在這裡，不是因為差 6 則有什麼影響，是因為這一整頁在講
「把政策寫成證據狀態」——用一個沒量過的數字支撐這個論點，是同一種病。

frontmatter 裡帶著 `thin_fact` 的實際是 6 則，按證據可得性分：

```
4 則  全部證據都是 withheld       AMD×3、Grok Imagine  → 不可能不薄
1 則  withheld ×2 + has_text ×1   OpenAI 數學十進展    → 有內文，是寫得薄
1 則  has_text，但還沒潤          Glassdoor            → status: dropped，門禁不再重算它
```

門禁每晚實際重算的是前 5 則（`dropped` 的那一則 blockers 是被丟棄那天凍住的）。

四則的共同點是：**它們永遠不會停止薄**。門禁每晚重算一次，每晚得到同一個
`thin_fact`，而 `thin_fact` 的意思是「去把事實寫厚一點」——那件事做不到，
因為我們選擇不取那些內文。看板上那條數字每天都在要求一個沒有人能做的動作。

### 拆成三個名字

| blocker | 什麼時候 | 誰該動 | 終端？ |
|---|---|---|---|
| `thin_fact` | 有任一筆證據拿得到內文 | 潤稿端：內容在手上，寫厚一點 | 否 |
| `thin_unfetched` | 一筆內文都沒有，而有來源是允許摘錄的 | 抓取端：這是我們的缺口 | 否 |
| `thin_by_policy` | 一筆內文都沒有，且全部來源都是政策不取 | **沒有人**。把話寫對就好 | **是** |

優先序是 `has_text` > `unfetched` > `withheld`，判準是**誰還有事可做**：
只要有任何一筆拿得到內文，薄就不是來源造成的。反過來排的話，一則
「三筆政策不取 + 一筆有全文」會被判成終端，而它其實寫得出來。

沒有 `evidence[]` 的事件維持 `thin_fact`——薄推不到來源身上，
而且 `missing_evidence` 會同時叫。

### `thin_by_policy` 進 TERMINAL_BLOCKERS

`pulse-monitor.py` 的 `TERMINAL_BLOCKERS` 原本只有 `stale_backfill`，
語意是「設計上就該永遠擋著，不是漏跑、也修不好——算警報會天天狼來了」。
`thin_by_policy` 完全符合這個定義，所以加進去。

量到的差別（同一份 vault，跑一次門禁前後）：

```
前   review=21（待處理=10／設計上擋著=11）  待處理最久=18 天
後   review=21（待處理= 6／設計上擋著=15）  待處理最久=14 天
```

「待處理卡最久的 5 則」原本前三名都是 AMD 那三則，18 天，而它們一天都不會少。
現在排頭是 `thin_research_analysis` 與 `generic_entity`——那兩件事有人做得動。

加進去之後那 4 則從「待處理卡關」移到「終端」計數，監看的紅綠不再被它們拉著。
**這不是把它們藏起來**：`_dashboards/blocked.md` 照樣列，名字還變得更精確了。
藏起來與不再誤報的差別在於，讀的人現在知道該去哪裡看它——
不是抓取端的待辦清單，是文章裡那句「原文在這裡」。

### `thin_unfetched` 今天是 0

上面那張表量出來，這條 blocker 今天一則都沒有。寫出來是因為
**這裡是最容易發生的一種靜默**：`excerpt_fetch` 每多開一條來源，
就多一批「該抓到而沒抓到」的事件，而它們會混進 `thin_fact` 裡，
長得跟「寫的人偷懶」一模一樣。selftest 用合成案例正反兩面釘住它。

### 沒動的：`thin_research_analysis`

它也會因為證據不可得而永遠掛著（`evt-2026-08-01-2a01f6` 就同時掛兩條）。
但那一則有 `has_text` 的證據，所以不是同一個病例；而且「影響/脈絡寫不寫得出來」
跟「事實段夠不夠長」的判準不同，硬套會判錯。留給下一支，這一頁不假裝它解決了。
