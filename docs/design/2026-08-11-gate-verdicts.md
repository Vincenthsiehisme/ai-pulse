# 2026-08-11 — 門禁裁決帳本（規劃，尚未實作）

> 起點是「用按讚／倒讚當好壞的調整因子」。這份文件把那個想法拆開，說明
> **為什麼原型不能直接做、以及重構成什麼形狀才配得上這個系統**。
> 尚未實作，也還沒排進 BACKLOG——先寫下來，等 `signal-review` 跑過一兩期再決定。

## 原始想法直接做，會撞上三件事

### 一、違反紅線 1

判斷由確定性規則決定。把票數餵進 `confidence` 或門禁，等於讓人氣決定發不發，
而這個系統存在的理由正是**不用人氣代理重要性**。`heat` 當初就佔著這個位置，
它從來沒接線反而是好事（規格 `references/readiness-gate.md`）。

### 二、樣本量

這個站的讀者是個位數。n=3 的票數沒有鑑別力，而這個 repo 剛剛花了兩輪，
把沒有鑑別力的數字從畫面上拿掉（`heat` 恆為未量測、`impact` 86/86 都是 55）。
**一個 n=3 的讚數比 heat 更糟**：heat 至少誠實說自己未量測。

### 三、架構

靜態站沒有後端。要存票就得接 Cloudflare Worker / KV 或表單服務——新的外部依賴、
新的失效模式，而且**票數住在 vault 外面**。「vault 是唯一真相源、全程可重現」
這個性質會當場破掉，而它是這個專案的核心宣稱。

## 重構：不是讀者投票，是操作者對門禁的裁決

把問題從「這則好不好看」換成「**這則該不該上線 / 那則不該被擋**」。

| | 讀者投票 | 門禁裁決 |
|---|---|---|
| 儲存 | 需要後端 | 寫進 vault，走 git |
| 樣本 | n=3 是雜訊 | n=1 就有意義（編輯判斷不是民調） |
| 可重現 | 不可 | 每一筆都在 commit 裡 |
| 紅線 1 | 違反 | 不改分數，只累積校準資料 |

它回答的是這個系統目前答不出來的一個問題：

> **86 則已上線的裡面有幾則其實不該發？19 則被擋的裡面有幾則其實該發？**

## 形狀（沿用既有的三個模式）

跟 `pulse-signal-review.py` 是同一個形狀，刻意的——這個 repo 已經有三個
append-only 帳本走 `lib/history.py`（來源層、判斷層、訊號裁決層），
這會是第四個，不另創格式。

```
_probe/gate-verdicts.jsonl     {at, id, field:"gate", from:<當時的 status>,
                                to:"should-publish"|"should-block"|"agree",
                                reason:<一句話>}
```

- **id ＝ event id**，不綁內容雜湊。理由跟 `signal-review` 相反：那裡問的是
  「這句話」，改寫過就是另一個問題；這裡問的是「這一則」，潤稿改了不影響
  它該不該上線。
- **`agree` 要能記**。只記不同意的話，分母不見了——「你看了 40 則、其中 5 則
  不同意」跟「你只看了 5 則、全部不同意」在帳本上會長得一樣，而這個 repo
  對「分母不見了」有紀錄（`references/health-alarms.md`〈量不到的年紀〉）。
- 產生待裁決清單與記錄裁決，兩個模式一支腳本，同 `pulse-signal-review.py`。

## 關鍵設計：不准自動調門檻

累積之後產出的是一份**報告**，不是一個自動迴圈：

> 本期標了 5 則「不該上線」，共同點是 `corroboration=20` 且 `facet=update`。
> 標了 3 則「不該被擋」，全部卡在 `thin_fact`。

**然後由人決定要不要改 `_config/gate.yaml`。**

自動調門檻的系統會安靜地漂移，而且沒有人解釋得出為什麼某一則突然上線了——
那正好違背這個 repo 花最多力氣守的東西：**判準是寫下來的、改動看得見、
每一次改都有理由**。`_config/gate.yaml` 的每個門檻旁邊都有一行註解寫著
消費者是誰，一個會自己動的門檻寫不出那行註解。

## 為什麼現在不做

1. **`signal-review` 還沒跑過一期。** 兩個帳本要一起設計才會一致，而現在還不知道
   人實際會怎麼用第一個。先做第二個，很可能兩個都要改。
2. **門禁本身還在動。** 這幾天才修掉 `thin_fact` 那個把 13 則卡死的重複標題，
   而 `blocked` 現在 19 則裡有 11 則是 `stale_backfill`（設計上就該擋著）。
   在門禁剛改完的時候收集「門禁判對了沒」，收到的是上一版的資料。
3. **先有分母才有意義。** 現在 86 則已上線裡，人一則都沒有複審過。第一批裁決
   應該是一次盤點（例如隨機抽 20 則）而不是逐日累積，否則早期資料會嚴重偏向
   「最近看到的那幾則」。

## 觸發條件

回來重讀這份文件。
