# 2026-08-11 — 主題追蹤重看一次：P1 的假設是錯的

> 這份取代之前只存在於對話裡的那份主題追蹤規劃。**那份規劃沒有進 repo**，
> 所以這個系統一直不記得這條線的存在——這正是這個 repo 一路在修的形狀。
> 現在它在 repo 裡了。

## 一句話

原本的 P1 是「把 `next_signal` 從散文變成結構化欄位，讓機器自動核對」。
實測之後，那句話裡有兩個事實錯誤，而且**瓶頸不在資料結構，在觀測範圍**。

## 錯誤一：那個欄位早就存在，而且從來沒被填過

```
frontmatter 的 next_signal 非空：0 / 86
body 的「## 下一個訊號」有內容：86 / 86（平均 41 字）
```

`next_signal` 是 frontmatter 的一個 key，schema 裡有、`pulse-enrich-apply` 會寫。
兩個多月來它一次都沒有被填過，有內容的一直是 body 那一段散文。

所以問題從來不是「要不要加一個結構化欄位」。加了也只是多一個沒人填的欄位——
這個 repo 已經量過這隻病很多次（`scoring.value` 算了沒人讀、判斷層帳本寫了
沒人讀、`_github/desc-zh.json` 從來沒出現過）。

## 錯誤二：填了之後，沒有東西能回答它

86 則已發布事件的「下一個訊號」，語言形狀是這樣：

```
「看有…」25   「看 …」14   「留意…」7   「看這…」6   「看是…」3   「看後…」3
```

**約六成以「看」開頭。它們不是述句，是祈使句**——寫給人的觀察指示，
不是機器可判定的命題。內容品質其實很好：

> 第三方在真實 codebase 的漏洞命中率與誤報數據。
> 看有沒有第三方（顧問公司、企業 IT）真的拿這套指標做採購決策，還是只停在 OpenAI 的部落格。
> 看具名的工廠、金額、時程這類可查事項，而不是宣示。

但它們指向的，全部是**這條抓取鏈看不到的世界**。

### 用系統自己的數字說同一件事

| 獨立來源數 | 則數 |
|---|---|
| **1** | **81（94%）** |
| 2 | 3 |
| 3 | 1 |
| 4 | 1 |

連最機械、系統本來就在算的那種後續——**第二個彼此無關的來源講同一件事**——
都只在 6% 的事件上發生過。

原因在來源組成：32 條裡官方部落格 16、媒體 7、KOL 8、聚合 1。
**官方部落格不會報導別人的 benchmark 結果、不會報導供應鏈出貨、
不會報導第三方採購決策**，而 next_signal 寫的正是這些。

**把散文變成 JSON，不會讓這個系統多看到任何一件事。**

## 所以這一版做的是別的東西

`scripts/pulse-signal-review.py`：把該問的問題整理成待回答清單，人回答，
答案進 `_probe/signal-verdicts.jsonl`。**它不自動判定任何事。**

三個裁決值：`happened` / `not-yet` / `unanswerable`。

`unanswerable` 是這裡最有價值的那一個。它累積出來的清單，就是
**「這個系統的觀測範圍看不到哪些東西」**的實測結果。幾期之後那份帳本會回答
一個現在只能用猜的問題：自動核對到底值不值得做、以及該先接哪一類來源。

**取得判斷的證據，比先做出一個猜出來的功能便宜。**

## 未解前沿

### 一、觀測範圍才是天花板（尚未決定要不要做）

94% 單一來源這件事，同時卡住三個東西：

- `corroboration` 永遠 20（81/86）
- `confidence` 永遠 73（79/86）→ 頭條選法退化成「取最新」（見 `pulse-render.pick_lead`）
- next_signal 永遠等不到後續

接上 benchmark / 論文 / 供應鏈 / 第三方評測類的來源，是**唯一能同時鬆開這三個**
的動作。但這是來源層的題目，牽涉抓取禮貌、robots、來源生命週期、以及一整批
新的去重問題（媒體轉載會讓 `independent_sources` 虛胖，那正是
`suspected_reposts` 在防的東西）。

**要先想清楚再動**，這份文件不預先決定。相關規格：
`references/source-lifecycle.md`、`references/evidence-tiers.md`。

順帶一個待查：32 條來源**沒有一條是 `active`**，全部停在 `probing` / `dormant`。
是設計（一直在試用期）還是晉升那條路沒接線，目前沒有量到答案。

### 二、深度報告本身

`_dashboards/signal-review.md` 是報告的**原料**不是報告。真正的報告要等
兩件事：判斷層帳本累積夠深（現在 18 筆、涵蓋 5 天），以及上面那份裁決帳本
累積出至少兩期。在那之前寫報告產生器，寫出來的會是一份沒有回顧的流水帳。

### 三、`impact_hint` 沒有接線

跟這條線無關但同時發現：`impact` 86/86 都是 55，因為它是
`scoring.score_event(impact_hint=55)` 的預設值而沒有任何呼叫端傳過它。
已從讀者頁面下架，接線與否見 `references/readiness-gate.md`。
