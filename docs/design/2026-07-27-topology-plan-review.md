## `判準歸屬`

計畫 §13 的 Gap type 表裡，**至少三個已經有實作在跑，而且比計畫的 predicate 更嚴謹**：

| Gap type | 現有擁有者 | 門檻住哪 |
|---|---|---|
| `dict_gap` | `lib/dictgaps.py`（判準）＋ `pulse-dictionary-gaps.py`（產出） | `gate.yaml.clustering.unknown_entity` |
| `no_source` | `pulse-monitor.py` | `sources.yaml.coverage_watch` |
| `silent` | `pulse-monitor.py` | 同上，可逐條覆寫 |

差距不只是「計畫寫得比較粗」。計畫 §14 的 `is_no_source(node)` **沒有觀察期守衛**，
而 monitor 有兩個：

- `silent_pending_clock`——用每條實體自己的 `first_fetch_at` 當尺，不是拿語料庫總長度。
  那正是 `fix/coverage-uses-own-clock` 修掉的洞。
- `alerting`——標了 `pending` 的不觸 exit code。理由寫在那段註解裡：**天天紅的燈
  等於沒有燈。**

照 §14 原樣實作，新 topology 第一次跑的那天會整片亮紅，然後人會學會忽略它。

但真正的風險不是這個，是**兩份實作並存**。`lib/dictgaps.py` 的 docstring 已經把這個
失效形態寫死了：抄一份的失敗形態這個 repo 已經量過三次，兩邊在門檻沒動過的日子裡
給一樣的答案，正好在有人調了其中一邊的那天分岔，**而不會有任何東西變紅**。

**拍板內容**：在那份 topology 規格檔裡加一節「判準歸屬表」，逐個 Gap type 寫明
擁有者。建議 `dict_gap` 留在 `dictgaps.py`、`no_source` / `silent` 留在 `monitor`，
topology 只**讀輸出**組成 Gap Graph、不重推。這一條會砍掉計畫大約三分之一的實作量，
而且符合 §3.4 的精神——只是把「設定檔單一真相源」延伸成**判準單一實作源**。

計畫 §28 已經有「關閉 planner 後現有收錄鏈可完全獨立運作」這條驗收，它跟這個修法
是同一個方向：**讀而不擁有，才真的關得掉。**

`BACKLOG.md` 的 `pending-覆蓋` 那 20 條，就是 `no_source` 的既有答案。

## `共現掃描範圍`

`_config/entities.yaml` 現在有兩個消費者、掃不同欄位（現況細節見 `BACKLOG.md` 的
`字典掃描範圍分岔`）。計畫層要拍板的是：**共現層用哪一個。**

拿現有語料、套計畫 §10.2 的門檻（≥2 events ＋ ≥2 independent voices）實測：

| 掃描範圍 | 命中 ≥2 實體 | 共現 pair | 過門檻 | 其中非宣告（真新增） |
|---|---|---|---|---|
| 標題（cluster 現行） | 6% | 42 | 2 | 1 |
| 標題＋摘要（probe 現行） | 18% | 120 | 14 | **10** |

**十倍。** 而且標題＋摘要跑出來的非宣告 pair 是有內容的：`deepseek×kimi`、`glm×kimi`
（中國模型實驗室彼此）、`transformers×vllm`（框架生態）、`google×microsoft`、
`claude-code×codex`（競品）。這些 `entities.yaml` 都沒宣告，是真的新知識。

這一條排第二只有一個理由：**沒有它，整層的價值評估會建立在錯的數字上。** 審查第一輪
就是用標題 only 量的，因此差點建議把共現層整個排到最後——那個建議是錯的（見末節）。

**口徑警告，寫進拍板紀錄**：上表跑在 07-25~07-27 加密班（一天 12 班）的語料上，
那是這個 vault 至今最密的三天。收班回一天一班之後，慢速來源（官方 blog、IR）不會漏，
但 HN frontpage 這種捲得快的會漏掉當天中段——而聚合站正是共現原料最密的地方。
**所以上表是上界，不是常態。** 重量指令在 `BACKLOG.md` 最後一節。

## `搜尋後端未指定`

§20.5 `pulse-search-adapter.py` 的職責寫了五條，**沒有一條說用什麼搜**。

這是計畫裡唯一一個會**改變專案性質**的決定。這個系統對外宣稱的身份是「零 API 成本、
可離線、可重現、全程可審計」；搜尋後端會引入第一個付費／限流／需要網路出口的外部
相依，而且要正面對上紅線 #7（遵守 robots、不繞過 login／WAF／付費牆）——
`references/incidents/2026-07-24-arxiv-robots.md` 才剛付過這方面的學費。

PR5–7、Sprint 4–6、導入階段 C–E 全部壓在這個未指定的東西上。
**在這題答完之前，PR5 之後都不該開工。**

拍板要回答四件事：用什麼、成本、robots 立場、以及它跟「零 API 成本可離線」的關係——
是修正那個宣稱（紅線 #8：不把做不到的講成做得到），還是把 adapter 設計成**可完全
關閉的選配**，讓不開它的人仍然拿到一個零成本可離線的系統。建議後者。

## `planner-以班為單位`

穩態是 `0 16 * * *`，**一天一班**，而且只能在 16:00Z——`_corpus/<UTC 日>/` 的目錄名
必須等於它裝的那個台北日，selftest 擋著（`references/timezones.md`〈排程〉）。

所以 §16 的 `expires_at = created_at + 7 天` 實際意思是**七次機會**，不是「七天內有很多次」。
把它跟導入階段 D 的「每班限制最大執行數」擺在一起看：**每班上限就是整個系統的搜尋
吞吐量上限。** 而 `pending-覆蓋` 已經有 20 條在等，全部會落在 P0/P1。每班上限若設
2–3，光排完 P0/P1 就要一週以上，P2/P3 的 plan 會在被排到之前就過期。

§27.4 有 `plans_expired` 這個指標（很好），但它會亮在一個不是真問題的成因上——
而「指標亮在錯的成因上」比沒有指標更糟，因為它會把人送去修錯的東西。

**拍板**：expiry 直接用**班數**表達，或每班上限必須大於 P0/P1 的消化速率。兩者擇一，
但不能兩個都用天。

順帶一個被日班節奏放大的東西：兩小時一班時，一班掛掉損失兩小時；一天一班時，一班
掛掉損失一整天，而且 `_corpus/` 那天不會有目錄、歷史留洞。所以 §25「Adapter 失敗
不影響既有收錄鏈」在日班節奏下是硬需求，要用**程式結構**保證——獨立 entrypoint、
不 import 收錄鏈的 write path、失敗只 log 不 raise——不是靠 try/except 兜。
計畫把 adapter 排在最後（PR6）是對的順序。

## `source_ineffective-假陽性`

§13 把 `source_ineffective` 定義成「來源持續成功抓取但長期無實體命中」。這個判準
分不出兩件事：**這條來源真的空轉**，還是**字典沒收它的守備範圍**。

用標題 only 量，多數語料命中 0 個實體（標題＋摘要下會低一些，沒有分開量，不編造）。
不管用哪個口徑，這個判準都會系統性地誣賴守備範圍最新的來源——而那些正是最該留著的，
因為新領域的來源本來就會先於字典出現。

**拍板**：`source_ineffective` 成立前要先排除「該來源的語料裡有高頻未收錄詞」——
而這正好是 `pulse-dictionary-gaps.py` 已經在算的東西。又一次指向 `判準歸屬`：
讀它，不要重算。

## `region-封閉集`

好消息是資料在：來源都帶 `region`（US／EU／global／CN／UK）。缺的是 `entities.yaml`
沒有 region 的 canonical 封閉集，所以 §7 的 `located_in`（Entity→Region）跟
`covers_region`（Source→Region）兩邊的 id 對不齊，會製造**假 dangling edge**——
而 §12.1 說 dangling 要紅燈、禁止進 planner。第一次跑就一片紅，然後人會學會忽略它，
連帶忽略真正的 dangling。

計畫 §22 自己也把 Region／Technology 節點頁列成「正式動工前的必要項」，
這一條只是把它從「節點頁」擴大到「id 封閉集」——**頁面可以晚點生，id 不行。**

## `id-命名空間`

§5 的範例把節點 id 寫成 `entity-openai`，但同一段的 `source_of_truth.key` 是
`companies.openai`，而 repo 裡還有 `Actors/` 頁自己一套檔名。三套命名如果各自演化，
會在半年後變成一張沒人敢動的對照表，而且**不會有任何東西變紅**。

**拍板**：一開始就定死「節點 id ＝ `entity-<entities.yaml 的 id>`」，轉換寫成
`lib/topology.py` 裡的**一個函式**，其他地方一律呼叫它。這是這個 repo 一貫的
single source of truth，只是套在 id 上。

## `驗收測不到有用`

§30 Sprint 6 那六個「人不看 JSON 也答得出來」的問句是真正的成果定義，寫得很好。
但 §28 的驗收標準有一半測的是**格式良好**而非**有用**：「100% Gap 都有 deterministic
predicate」「100% Plan 都有 closes_when」——**一個只會產生垃圾 Gap 的引擎照樣 100%
通過。**

這是紅線 #8 的一個變形：不是把做不到的說成做得到，而是**用一個比目標寬鬆的代理指標
去代表目標**——跟 `BACKLOG.md` 開頭講的「為什麼這裡沒有編號」是同一隻病。

**拍板**：§28 補一條可證偽的成果條件。建議形狀是「首 N 班產出的 P0/P1 Gap，人工複核
假陽性率低於 X%」——它會逼 Gap predicate 對準真問題，而不只是對準 schema。

## 附：查過、不成立

紅線 #8 說驗證不出來的懷疑就寫「查過、不成立」，不要硬送假問題。以下四條包含審查
過程中自己講錯、後來查掉的話。留著是因為下一個人（或下一個我）會再想到同樣的懷疑，
而重查一次要花的時間比讀這一節長。

**「Observation Graph 現在編不出來，要新建一道實體解析」——不成立。**
`lib/entities.py` 的 matcher 早就存在，`pulse-cluster.py` 與 `pulse-probe.py` 都在用。
缺的只是持久化（`BACKLOG.md` 的 `實體命中用過即丟`），那是持久化改動，不是新子系統。

**「共現層產出太稀，應該排到最後」——不成立。**
那個結論是用標題 only 量出來的。改用 probe 已經在用的標題＋摘要，同一份語料、同一組
門檻，非宣告新邊多一個量級。正確的動作不是延後這一層，是先拍板掃描範圍
（見 `共現掃描範圍`）。

**「執行節奏要拆開：topology 每班編、Gap／Plan 降到一天一次」——不成立。**
穩態就是一天一班（`0 16 * * *`），§25 那 14 步走在同一班裡是對的。當時看到的
`0 */2 * * *` 是 07-25~07-27 的臨時加密班，收班任務排在 07-27 12:00Z，另有每週自癒的
禮貌檢查兜底——理由寫在 `data-refresh.yml` 的檔頭。**計畫在這點上是對的，審查是錯的。**

**「`sources.yaml` 沒有 region 資料」——部分不成立。**
來源都有 `region` 值，缺的只是 canonical 封閉集（見 `region-封閉集`）。

## 附：計畫裡不必改的兩處

審查不只找問題。這兩處建議原樣保留：

- **§32「第一版明確不做」那十二條**——不用 embedding 建邊、不用 LLM 判關聯、
  不自動把 candidate 升成 core、不以搜尋結果數量代表成功。這是很乾淨的範圍聲明，
  而且每一條都直接對應紅線 #1 或 #8。
- **§28「關閉 planner 後，現有收錄鏈可完全獨立運作」**——正確的隔離紀律，
  而且它剛好支持 `判準歸屬` 的修法：讀而不擁有，才真的關得掉。
